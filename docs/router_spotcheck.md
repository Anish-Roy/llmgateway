> ### What is a virtual environment in Python?
>
> A **virtual environment** (often shortened to *venv* or *virtualenv*) is an isolated, self‑contained Python runtime that contains:
>
> - Its own **Python interpreter** (or a symlink to a shared interpreter)
> - Its own **site‑packages** directory (where third‑party libraries are installed)
> - Its own **configuration files** (e.g., `pyproject.toml`, `setup.cfg`, `requirements.txt`)
>
> In other words, a virtual environment lets you **install, upgrade, or remove packages without affecting the global (system‑wide) Python installation or any other projects** on the same machine.
>
> ---
>
> ## Why Use a Virtual Environment?
>
> | Problem | Why it matters |
> |---------|----------------|
> | **Dependency Hell** | Two projects may need different versions of the same package. Installing both globally would cause conflicts. |
> | **Reproducibility** | A virtualenv can be frozen to a `requirements.txt` or `Pipfile.lock`, ensuring that anyone else (or a CI/CD pipeline) can recreate the exact same environment. |
> | **Security & Safety** | Installing packages globally can inadvertently modify system files or expose the system to malicious packages. Virtualenvs keep everything sandboxed. |
> | **Multiple Python Versions** | You might need Python 3.7 for one project and Python 3.10 for another. A virtualenv can target a specific interpreter. |
>
> ---
>
> ## Key Components
>
> | Item | Typical Path in a Virtual Environment | What It Does |
> |------|----------------------------------------|--------------|
> | **Python interpreter** | `bin/python` (Unix) / `Scripts/python.exe` (Windows) | Executes your code. Often a symlink to the system Python. |
> | **pip** | `bin/pip` / `Scripts/pip.exe` | Package installer that writes to the env’s `site‑packages`. |
> | **site-packages** | `lib/pythonX.Y/site-packages` | Directory where all installed third‑party packages live. |
> | **activate** script | `bin/activate` / `Scripts/activate.bat` | Sets environment variables to use the env’s interpreter. |
> | **deactivate** | Built‑in command when the env is active | Restores original shell environment. |
>

> ### What is `top_p`?
>
> `top_p` (sometimes called **nucleus sampling**) is a parameter that controls the randomness of the next token chosen by a language‑model API.
> It tells the model to look at the *cumulative probability mass* of the token distribution and pick a token from the smallest possible set of tokens that together account for at least a proportion `p` of that mass.
>
> ```
> top_p = 0.9  →  include the smallest set of tokens that make up 90% of the total probability
> ```
>
> ### Why is it useful?
>
> - **Avoids overly deterministic outputs** that come from a pure greedy strategy (`top_k = 1` or `temperature = 0`).
> - **Avoids too many low‑probability tokens** that would make the text nonsensical, which can happen with a very high `temperature` or a very large `top_k`.
> - Gives you a single knob that balances *creativity* (higher `top_p`) and *coherence* (lower `top_p`).
>
> ### How it works (step‑by‑step)
>
> 1. **Get the probability distribution** for the next token from the model.
>    This is a list of all possible tokens with their probabilities \(P(t)\).
>
> 2. **Sort tokens in descending order of probability.**
>
> 3. **Accumulate probabilities** until the cumulative sum reaches or exceeds `top_p`.
>    The set of tokens considered is called the *nucleus*.
>
> 4. **Sample uniformly or weighted** (according to the original probabilities) from this nucleus to pick the next token.
>
> 5. **Append** the chosen token to the generated text and repeat for the next position.
>
> ### Practical effects
>
> | `top_p` value | Typical behaviour |
> |---------------|-------------------|
> | **≤ 0.5** | Very conservative. Almost always picks the top 1–2 tokens. |
> | **0.5 – 0.8** | Moderately conservative. Allows a few plausible alternatives. |
> | **0.8 – 0.95** | Balanced. Good for creative writing while still staying on topic. |
> | **> 0.95** | Very creative, sometimes surprising, but can become incoherent. |
>
> ### Common combinations
>
> | `temperature` | `top_p` | Effect |
> |---------------|--------|--------|
> | 1.0 (default) | 0.9 | Standard creative sampling. |
> | 0.7 | 0.8 | More focused, slightly less random. |
> | 1.5 | 0.9 | Very high creativity, may generate odd phrases. |
> | 0.0 | 1.0 | Greedy decoding (no randomness). |
>
> ### Tips for tuning
>
> - **Start with `temperature = 1.0` and `top_p = 0.9`.**
>   This is the most common “balanced” setting.
>
> - **If you want more deterministic output**, lower `top_p` (e.g., 0.6–0.7) or set `temperature = 0`.
>
> - **If you want more novelty**, raise `top_p` (e.g., 0.95–0.99) or increase `temperature`.
>
> - **Watch the token distribution shape**: If you notice the model is consistently picking a handful of tokens, consider lowering `top_p`. If it’s outputting random, unrelated words, consider raising `top_p` or lowering `temperature`.

> ## 1. The intuition behind `top_p`
>
> When an LLM generates text it first computes a probability distribution over its entire vocabulary for the next token.
> - **Greedy decoding** would always pick the single highest‑probability token.
> - **Temperature‑scaled sampling** (with `temperature` > 0) adds randomness but still draws from the whole distribution, including very low‑probability tokens that can produce nonsensical output.
>

>
> 1. Sort the vocabulary tokens by their probability (highest → lowest).
> 2. Starting from the top, keep adding tokens until the sum of their probabilities reaches (or exceeds) `p`.
> 3. Discard everything else.
> 4. Re‑normalize the kept probabilities so they sum to 1 and sample from that reduced set.
>
> If `p = 0.9`, you keep just enough tokens to cover 90 % of the total probability mass. The exact number of tokens kept varies from step to step and from prompt to prompt; sometimes it might be a handful, other times a few dozen.

> **Binary Search in Python**
>
> Binary search works on a *sorted* sequence and repeatedly halves the search interval until the target element is found (or the interval becomes empty).
> Because the interval size is cut in half each step, the algorithm runs in **Θ(log n)** time, where *n* is the number of elements in the list.
>
> ---
>
> ## Implementation
>
> ```python
> def binary_search(arr: list[int], target: int) -> int:
>     """
>     Perform binary search on a sorted list `arr`.
>
>     Parameters
>     ----------
>     arr : list[int]
>         A list that must be sorted in non‑decreasing order.
>     target : int
>         The value we are looking for.
>
>     Returns
>     -------
>     int
>         The index of `target` in `arr` if it exists; otherwise -1.
>
>     Time Complexity
>     ---------------
>     O(log n) – each iteration discards half of the remaining elements.
>     Space Complexity
>     ---------------
>     O(1) – only a few extra variables are used (iterative version).
>     """
>     left, right = 0, len(arr) - 1
>
>     while left <= right:                # while there is a search interval
>         mid = left + (right - left) // 2  # avoid overflow in other languages
>         mid_val = arr[mid]
>
>         if mid_val == target:            # found!
>             return mid
>         elif mid_val < target:           # target is in the right half
>             left = mid + 1
>         else:                            # target is in the left half
>             right = mid - 1
>
>     # target not present
>     return -1
> ```
>
> ### How it works
>
> | Step | `left` | `right` | `mid` | `arr[mid]` | Action |
> |------|--------|---------|------|------------|--------|
> | 1    | 0      | n‑1     | (0+n‑1)//2 | … | Compare with `target` |
> | 2    | …      | …       | …    | … | Discard the half that cannot contain the target |
> | …    | …      | …       | …    | … | Repeat until `left > right` |
>
> If the element exists, the loop exits with `return mid`.
> If the element does **not** exist, the loop ends when `left` passes `right` and we return `-1`.
>
> ---
>
> ## Time‑Complexity Proof (O(log n))
>
> Let *n* be the length of `arr`.
>
> * After the first iteration the search interval size is at most `⌈n/2⌉`.
> * After the second iteration the size is at most `⌈n/4⌉`.
> * After *k* iterations the size is at most `⌈n/2^k⌉`.
>
> The loop stops when the interval size becomes 0, i.e.
>
> ```
> n / 2^k < 1   →   2^k > n   →   k > log2(n)
> ```
>
> Thus the number of iterations `k` is bounded by ⌈log₂ n⌉, which is Θ(log n).
> Each iteration does only O(1) work (a few arithmetic operations and comparisons), so the overall time complexity is **O(log n)**.
>
> ---
>
> ## Space Complexity
>
> The iterative version uses only a constant amount of extra variables (`left`, `right`, `mid`, `mid_val`).
> Hence **O(1)** auxiliary space.
>
> *(A recursive version would use O(log n) stack space because each recursive call adds a frame.)*
>
> ---
>
> ## Quick Demo
>
> ```python
> if __name__ == "__main__":
>     sorted_list = [2, 5, 7, 12, 19, 23, 31, 45, 56, 78]
>     for x in [7, 23, 50, 78]:
>         idx = binary_search(sorted_list, x)
>         if idx != -1:
>             print(f"{x} found at index {idx}")
>         else:
>             print(f"{x} not found")
> ```
>
> **Output**
>
> ```
> 7 found at index 2
> 23 found at index 5
> 50 not found
> 78 found at index 9
> ```
>
> ---

> * You need fast look‑ups and are willing to pay the cost of keeping the data sorted (insertion/deletion become O(log n) if you maintain a balanced tree, otherwise O(n) for a plain list).
